# Disclaimer — Ownership and Responsibility

Kasten provides **Kanister**, a framework for application-aware data protection, and the
integration of that framework into the product. Kasten is responsible for maintaining Kanister
and its integration as part of the product.

**Blueprints, however, are entirely owned by the customer.** A blueprint is custom logic written
by (or on behalf of) the customer and executed against their own databases. Kasten cannot be held
responsible for any data loss or corruption resulting from a blueprint that is incorrect,
destructive, or that fails to properly quiesce or protect a database. Validating that a blueprint
backs up and restores correctly — including the end-to-end testing described in `AGENTS.md` — is
the customer's responsibility before using it in production.

The relationship is analogous to Microsoft providing the C# language and its surrounding
framework: Microsoft maintains the language and runtime, but in no case is Microsoft responsible
for the destructive behavior of a C# program written by one of its customers. The same boundary
applies here between Kasten/Kanister (the framework) and the blueprints (the customer's program).

This boundary is why every blueprint directory in this repository is suffixed with `-example`:
each one encodes the operator version, CR layout, storage class, credentials, namespace topology,
and consistency level of the deployment it was developed against, and is therefore a starting
point to be adapted and re-validated — never a turnkey solution to be applied as-is.

# Container images

Some blueprints need a tool image that the standard `gcr.io/kasten-images/kanister-tools` image
does not provide (`kubectl`, `jq`, `etcdctl`, `cpdctl`, and so on). Those images are built by the
workflows in [.github/workflows/](.github/workflows/) and published publicly under
`ghcr.io/kastenhq/blueprint-ai/`, so the blueprints work as shipped with no image build required.

Two layouts, described in [AGENTS.md](AGENTS.md#step-4--implement-blueprint-and-document-dependencies):

- **Shared image**, used by several blueprints → one canonical Dockerfile at
  [images/kasten-tools/](images/kasten-tools/).
- **Blueprint-specific image**, when the shared one cannot work → `<blueprint>/images/<name>/`,
  for example [ocp-etcd-backup-example/images/ocp-etcd-backup/](ocp-etcd-backup-example/images/ocp-etcd-backup/).

> **Air-gapped, or running a Kasten version we have not published?** Every image has a committed
> `Dockerfile` and the owning blueprint's `README.md` documents the exact `docker build` /
> `docker buildx` command, including the build args that pin the Kasten, Kubernetes, and tool
> versions — so you can build and host every image yourself. Push to **your own** registry and
> update the `image:` fields accordingly; pushing to `ghcr.io/kastenhq/blueprint-ai/...` will fail
> with `unauthorized`, since that registry belongs to this repository's CI.
> [images/kasten-tools/README.md](images/kasten-tools/README.md) covers retargeting the whole repo
> at your registry in one command, and the cluster-level alternatives (registry mirrors,
> `ImageDigestMirrorSet`) that need no file edits at all.

# Prompting

All the blueprints in this repository were generated by prompting an AI coding agent. Read
[AGENTS.md](AGENTS.md) for our opinionated way of creating blueprints, and
[kasten-kanister.md](kasten-kanister.md) to understand the integration of Kanister in Kasten.

`AGENTS.md` is the cross-agent instruction file (the open standard honored by most AI coding
agents). For Claude Code, `CLAUDE.md` imports it through `@AGENTS.md`, so there is a single source of
truth.

The agent will interact with you for the architecture decisions but is autonomous during test and
troubleshooting.

## Sample Prompts

**Note on the prompts below.** The prompts listed in this README are **illustrative examples**,
not a verbatim transcript. We do not report every prompt that was used to produce a blueprint,
and we do not reproduce the back-and-forth conversation that happens when we settle on the
architecture (pattern choice, trade-offs, corrections). They are here to give you a sense of the
intent behind each blueprint — the authoritative output is the committed code and each
blueprint's `README.md`.

### DB2u on Maximo

Can you make a blueprint for backing up DB2 on Maximo with a dump.
You do not have to install the database and create test data. They are already provided by Maximo. Only use the current context and the db2u namespace.
For your restore test you should find a description field and alter it to see that your alteration is reverted.
It seems (but that needs confirmation) that a backup PVC already exists. The pattern 3 (Database snapshot on a permanent PVC) comes naturally.
The starting point for the IBM documentation is here: https://www.ibm.com/docs/en/db2/11.5.x?topic=ad-backing-up-restoring-db2
We want to be able to restore on another Maximo instance. We also need to manage the encryption keystore https://www.ibm.com/docs/en/db2/11.5.x?topic=ad-locating-keystore
but I do not know exactly what it is and how we should include this artifact in the backup/restore process. This you need to discover and explain.
You do not have to restore db2u in another Maximo instance, but you must bring extra instructions on how it should be restored on another instance to ensure that
the client applications that connect to this instance do not have to renew their truststore.
